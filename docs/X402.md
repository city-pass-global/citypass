# Agent purchases with x402

Implemented for **Stellar testnet only**, behind `X402_ENABLED=1`. This is a second payment rail for existing published destination passes, not a new entitlement or a paid check-in. Published offers remain exactly **100 testnet USDC**, with the existing +80 non-transferable reputation rule and no venue admission or discounts.

## Traveler authorization

Visit `/en/passport/agents` (also `/es` and `/pt`) while signed in with Pollar and with an active passport. Select the current destination's published pass and enter the **dedicated agent's public Stellar wallet**. Consent creates one order with a 15-minute deadline, fixed price, approved offer recipient and frozen beneficiary wallet. The agent wallet needs testnet USDC and its trustline; it is independent of the traveler's managed Pollar wallet.

Copy the endpoint and Bearer credential to the agent securely. Only a hash is stored in PostgreSQL. The raw credential is shown only on creation, never placed in a URL or logged. It grants no access to passport history, memberships, hotel records or other purchases. The authorization history allows revocation before payment processing starts. Leaving the page does not revoke a credential.

The UI and authorize/revoke actions require the normal database-backed application session. Agent requests use **only** the separate purchase credential in `Authorization: Bearer …`; never give an agent the app session cookie or a traveler's private key.

## API

`GET /api/agent/passes/{request_id}` with the purchase Bearer credential:

- `402` + `PAYMENT-REQUIRED`: x402 v2 `exact` requirements for `stellar:testnet` and the USDC SAC.
- Retry with `PAYMENT-SIGNATURE` containing the signed contract authorization.
- `200` + `PAYMENT-RESPONSE`: independently verified chain settlement and atomic pass fulfillment. The existing activity worker publishes the beneficiary's reputation automatically.
- `202`: settlement/confirmation pending; no pass is granted yet. Read `recovery_required` and poll the same order. Never initiate another payment for it.
- `401/403`: missing or incorrect credential; `410`: revoked/expired; `409`: another request already started payment; `503`: configuration/provider/database unavailable.

Paid requests are checked against server-generated requirements and the exact order resource. Local validation accepts only one USDC SAC `transfer` from the approved agent to the frozen recipient for the exact amount, with one address authorization and no nested calls. The facilitator verifies signatures and simulates settlement. PostgreSQL persists the accepted signed payload before external settlement, and permits exactly one transition into processing.

The backend independently reads Stellar RPC `SUCCESS`, the envelope hash, ledger/time bounds, the exact transfer and the **same signed authorization entry** before signing database evidence. Only then does the receipt transaction grant one holding, one reputation award and one queued activity for the frozen beneficiary wallet. Unique transaction hashes prevent reuse across receipts. Classic checkout signing and evidence endpoints cannot operate on an x402 order.

No browser callback or facilitator success message alone grants a pass. Signed payloads remain private and are never returned in the agent API response.

## Agent CLI

Pinned SDK dependencies: `@x402/core`, `@x402/stellar`, `@x402/fetch` 2.28.0. The agent SDK uses its own compatible Stellar SDK internally; app-side proof verification uses the project's SDK 17 APIs and exchanges wire XDR only.

Set these in an ignored environment file on the **agent's machine**:

```dotenv
APP_ORIGIN=http://localhost:3000
X402_AGENT_SECRET=<dedicated testnet agent secret>
X402_PURCHASE_TOKEN=<traveler-created credential>
X402_PURCHASE_URL=http://localhost:3000/api/agent/passes/<request-id>
```

Run `npm run x402:agent`. It refuses another origin/network/asset or any amount other than 100 USDC. It writes the signed authorization to ignored `.x402/{request-id}.json` with mode 600 before transmission; retries reuse it rather than signing another payment. Keep this file private. The CLI never exports a Pollar key or logs credentials/payment payloads. Run only one CLI process per purchase.

By default the server uses the public `https://www.x402.org/facilitator`, whose `/supported` endpoint was checked on 2026-10-25 and advertised `stellar:testnet` with sponsored fees. The server checks support again when generating requirements. Optionally configure `X402_OZ_API_KEY` to use `https://channels.openzeppelin.com/x402/testnet`; it requires its own key. Credentials are sent only to that fixed OZ endpoint, never an arbitrary configured URL. An external facilitator receives the signed payment authorization; see Stellar's official [facilitator guide](https://developers.stellar.org/docs/build/agentic-payments/x402/built-on-stellar) and [quickstart](https://developers.stellar.org/docs/build/agentic-payments/x402/quickstart-guide).

## Indeterminate settlement recovery

If a facilitator times out after processing begins, the order remains `settling`. The system **does not** accept a fresh payment or clear that state merely because the authorization expired. This avoids charging twice. If a hash was received, subsequent GETs independently check it and finish the original receipt.

If the response was lost before its hash was persisted, retrieve the original settled transaction hash from the agent wallet's chain history/facilitator support and send:

```http
POST /api/agent/passes/{request_id}
Authorization: Bearer <purchase credential>
Content-Type: application/json

{"transaction_hash":"<original settled transaction hash>"}
```

The server checks the on-chain transfer and the original persisted signed authorization **before** binding that hash. A different payment cannot be substituted. No additional transfer is submitted. Fully automatic reconciliation of unknown hashes, release after proven failed/expired authorization, refunds, and background confirmation polling are not yet implemented. A definitive failed payment also stays blocked for review; do not treat this as mainnet-ready.

## Reflector

The current offer is denominated and settled in USDC, so no oracle is needed. Using Reflector to display USDC as USD is not a guarantee of the USDC/USD peg. If future offers use local currency or accept XLM, use `@reflector/contract-client` to discover supported feed assets, read decimals and fresh quotes, calculate with integers and freeze the resulting USDC quote/deadline in the order. Reject missing/stale feeds; never silently fall back to invented FX rates. No Reflector quote is used in this version.

`X402_ENABLED=1` is set in the local ignored `.env.local`, and the app has been restarted. Production/mainnet deployment is not authorized by this implementation.
